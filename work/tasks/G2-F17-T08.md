## 1. 배경

### 1.1 사용자 문제

ZIP은 파일 이름의 인코딩을 기록하지 않는 경우가 많다([F17 1절](../../docs/05-feature-specs/F17-filename-encoding.md)). j-zip은 이름 바이트를 보고 가장 그럴듯한 인코딩을 자동으로 고른다. G2-F17-T03이 후보마다 점수를 계산했다. 이 카드는 그 점수로 **후보를 줄 세우고(UTF-8 확정, 동점 처리), 확신이 부족한지 판정하고, 화면에 보일 퍼센트와 "추천"·"기본값" 표시를 만든다.** 그리고 명세 샘플 이름 묶음(F17 8절)으로 "이름 바이트 → 감지 결과"를 끝까지 증명한다.

### 1.3 구현에 필요한 사실 (인라인)

**T03이 주는 것.** `ComputeCandidateScores(ScoringInput)`가 후보별 `CandidateScore{codePage, validityRate, plausibility, prior, score}`를 입력 순서대로 돌려준다. 점수는 `V x P′ + prior`(UTF-8은 P′ 1.0, `V < 0.9`인 DBCS는 prior만, 단일 바이트류는 `0.05 + prior`)이고 상한이 없다(최대 1.10). 입력이 잘못됐거나 이름이 없으면 `status`가 `kInvalidInput`·`kNoNonAsciiNames`이고 점수 목록이 비어 있다.

**순위 규칙**(FR-17-6, 10, 11, 12):

- UTF-8의 `V`가 1.0이고 다바이트 시퀀스가 2개 이상이면 UTF-8을 1순위로 확정한다(FR-17-6).
- 확정이 아니면 최고 점수와 0.02 이하 차이인 후보들 중 동점 순서(시스템 OEM → 949 → 65001 → 932 → 936 → 그 밖)가 앞선 후보가 1순위다(FR-17-10). **이 규칙은 1순위만** 정한다. 2순위 이후는 점수 내림차순이고 같은 점수일 때만 동점 순서를 쓴다.
- 1순위 점수가 0.6 미만이거나 2순위와의 차가 0.1 미만이면 "확신 부족"이다(FR-17-11). UTF-8이 확정된 경우에도 같은 식을 쓴다(FR-17-11이 우선).
- 표시 퍼센트는 `round(100 x min(score, 1))`, .5는 올림이다(FR-17-12). 1순위에 "추천", 7-Zip 기존 규칙 코드페이지에 "기본값"을 붙인다.

**호출 위치.** `ScoreCandidates`는 G2-F17-T04가 `ZipHandler` 열기 훅에서 호출한다. 그 훅과 이름 결정 순서(FR-17-13)는 이 카드 밖이다.

**명세 샘플.** F17 8절의 샘플은 `kr_ntfs.zip`(이름 CP949), `kr_unix.zip`(HostOS Unix, 이름 CP949, 이름 바이트는 `kr_ntfs.zip`과 같다), `utf8_noflag.zip`(UTF-8 바이트), `jp.zip`(Shift-JIS), `cn.zip`(GBK), `ascii.zip`(ASCII뿐)이다. HostOS가 Unix인 ZIP의 "7-Zip 기존 규칙 코드페이지"는 UTF-8(65001)이다(FR-17-9). 이 카드의 코퍼스는 ZIP 파일이 아니라 이름 바이트 목록이다.

### 1.4 작성 환경 한계

이 카드를 쓴 환경에는 C++ 컴파일러가 없어서 6절 선언을 컴파일해 보지 못했다. 8절의 기대값은 Python 참조 구현(카드 작성자가 T03 7절과 이 카드 7절 규칙을 그대로 옮긴 임시 스크립트)으로 계산한 값과 손계산이 일치함을 확인했다. 코퍼스의 이름 바이트가 각 코드페이지로 엄격하게 디코딩되고 8.2.1절에 적은 문자가 나오는 것도 그 스크립트로 확인했다. 스크립트는 레포에 넣지 않는다. `real` 표를 쓰는 행(8.2.1절)은 T09의 실제 표를 모르는 상태라 손계산이 아니라 명세 문장(F17 8절)이 기대값이다.

### 6.3 `SortedCharSet` — 제안(카드 결정)

`src/shared/encoding/sorted_char_set.h`(헤더 전용). T09의 정렬된 문자 목록을 `ICommonCharSet`으로 감싼다. G2-F17-T04가 점수기를 호출할 때와 이 카드의 통합 테스트가 쓴다.

class SortedCharSet final : public ICommonCharSet {
 public:
  // sortedChars는 코드 포인트 오름차순이다. 호출자가 소유하고 이 객체보다 오래 산다.

### 6.4 `ScoreCandidates` — 제안(시그니처는 카드 결정, 동작은 FR-17-6·10~12 확정)

`src/shared/encoding/candidate_ranking.h`.

```cpp
struct RankedCandidate {
  CodePage codePage = 0;
  double   validityRate = 0.0;    // V (T03 값 그대로)
  double   plausibility = 0.0;    // P' (T03 값 그대로)
  double   prior = 0.0;
  double   score = 0.0;
  int      displayPercent = 0;    // FR-17-12
  bool     isRecommended = false; // ranked[0]
  bool     isLegacyDefault = false; // codePage == context.legacyCodePage ("기본값")
};

struct DetectionResult {
  DetectionStatus status = DetectionStatus::kOk;
  std::vector<RankedCandidate> ranked;   // 순위 순서. status != kOk이면 비어 있다
  bool confident = false;                // FR-17-11. false이면 S1-12 칩이 "확인 필요"가 된다(화면은 G3-F17-T07)
  bool utf8Forced = false;               // FR-17-6이 적용됐는가
};

DetectionResult ScoreCandidates(const ScoringInput& input) noexcept;
```

- Input: T03의 `ScoringInput`. 사전조건은 T03 7.1절(이 함수가 `ComputeCandidateScores`를 먼저 호출해 확인한다). 이름 바이트(`string_view`)는 호출 동안만 읽고 보관하지 않는다.
- Output: `DetectionResult`. `status == kOk`이면 `ranked.size() == candidates.size()`.
- 오류: 예외를 던지지 않는다(`noexcept` + 함수 전체를 `try { … } catch (...) { return {kInternalError, …}; }`로 감싼다). T03이 돌려준 `status`가 `kOk`가 아니면 그 값을 그대로 담는다.
- 부작용: 없음. 파일·레지스트리·네트워크·OS 호출 없음, 전역 가변 상태 없음, 시계·난수 없음. Release에서는 로그도 없다(11절).
- 스레드: 재진입 가능, 입력이 `const`이므로 같은 입력으로 여러 스레드가 동시에 호출해도 된다.
- 성능: 문자 단위 힙 할당을 하지 않는다(결과 벡터 외 작은 보조 배열만 허용). 이름 2,000개 × 후보 5개의 전체 호출을 Release x64에서 20ms 이하(TC-16, 출처: 카드. F17 5절 50ms 중 이 단계 몫으로 카드가 정함).
- 내부 구조는 구현자가 정한다. 위 공개 타입과 동작만 계약이다. G2-F17-T04가 이 타입을 그대로 쓰므로 핸드오프 뒤 바꾸려면 카드 개정이다.

### 6.5 `Encoding.Detected` 이벤트 매핑 — 확정([10 2.2](../../docs/10-logging-evidence-operations.md) 이벤트 목록)

이 카드는 이벤트를 방출하지 않는다. 호출자(G2-F17-T04)가 `ranked[0]`에서 `candidate = codePage`, `score = score`, `confident = DetectionResult::confident`를 채워 `Encoding.Detected`(Verbose; opId, candidate, score, confident)를 남긴다.

## 7. 동작 명세

### 7.1 T03 결과 전달 (R-1) — 제안(카드 결정)

`ComputeCandidateScores`를 호출해 `status`가 `kOk`가 아니면 그 `status`와 빈 `ranked`, `confident = false`, `utf8Forced = false`로 돌려준다. 입력 검사는 T03이 하므로 이 카드는 다시 검사하지 않는다.

### 7.2 UTF-8 확정 (R-2) — 확정(FR-17-6)

`utf8Forced = true`가 되는 조건: 65001 후보가 있고, `validCount == totalCount`(V = 1.0)이고, 그 후보의 모든 `decoded[i].bytes`에서 `(바이트 & 0xC0) == 0xC0`인 바이트(다바이트 시퀀스의 선두 바이트)의 합이 2 이상이다. V = 1.0이면 모든 이름이 올바른 UTF-8이므로 선두 바이트 수가 시퀀스 수와 같다.

### 7.3 순위 (R-3) — 확정(FR-17-10, 1순위만) + 제안(2순위 이후의 구현 방식)

동점 순서표 `tieOrder(cp)`: 목록 `[systemOemCodePage, 949, 65001, 932, 936]`에서 0이거나 중복인 값(첫 등장만 유지)을 뺀 뒤, 코드페이지가 그 목록에서 몇 번째인지. 목록에 없는 후보(그 밖)는 `100 + <입력 candidates에서의 위치>`. 값이 작을수록 앞선다.

1. `utf8Forced`이면 UTF-8이 1순위다.
2. 아니면 `best = 최고 score`. `best - score <= 0.02 + kEpsilon`인 후보 집합에서 `tieOrder`가 가장 작은 후보가 1순위다.
3. 나머지 후보는 하나씩 뽑는다: 남은 후보의 최고 점수에서 `kEpsilon` 이내인 후보들 중 `tieOrder`가 가장 작은 후보를 다음 순위로 한다. 남은 후보가 없을 때까지 반복한다(후보 수가 작아 선택 정렬로 충분하다). — 2순위 이후는 "점수 내림차순, 같은 점수면 동점 순서"이며 S5-02의 "점수 내림차순"([F17 4절](../../docs/05-feature-specs/F17-filename-encoding.md))과 같다. 0.02 규칙은 1순위만 정한다.

### 7.4 확신, 퍼센트, 플래그 (R-4~R-6) — 확정(FR-17-11·12) + 제안(부동소수 처리)

- R-4 `confident`: 아래 둘 중 하나면 `false`, 아니면 `true`.
  - `ranked[0].score < 0.6 - kEpsilon`
  - 후보가 2개 이상이고 `ranked[0].score - ranked[1].score < 0.1 - kEpsilon` (차가 음수여도 같은 식. 동점 규칙이나 UTF-8 확정으로 점수가 더 높은 후보가 2순위가 된 경우)
  - UTF-8 확정(`utf8Forced`)인 경우에도 같은 식을 쓴다(FR-17-6의 "확정"과 FR-17-11을 모두 적용. 충돌하면 FR-17-11이 우선한다는 명세 보충). TC-02, TC-04.
- R-5 `displayPercent = (int) floor(100.0 x min(score, 1.0) + 0.5 + kEpsilon)`. `.5`에서 올림이다(예: 42.5 → 43, 24.5 → 25).
- R-6 `isRecommended = (순위 0)`, `isLegacyDefault = (codePage == legacyCodePage)`. 같은 코드페이지가 `legacyCodePage`인 후보가 입력에 없으면 어떤 후보도 `isLegacyDefault`가 아니다. `legacyCodePage`가 0이면 어떤 후보도 아니다.

#### 8.2.2 손계산 (기대값을 구현이 아닌 공식에서 얻었음을 보이는 풀이)

- **`kr_ntfs-en`(OEM 437, legacy 437, fixture)**: 감지 입력 이름 3개(모두 0x80 이상 바이트 있음). 전부 CP949로 유효(V = 1). 디코딩하면 한글 15글자(`발표자료최종` 6 + `보고서` 3 + `보고서장서론` 6)이고 모든 쌍의 첫 바이트가 B0~C7 사이라 0xB0~0xC8 안, 둘째 바이트는 A1~FE 안 → ksx 15, hangul 15, uhc 0 → P = 15/15 = 1.0. fixture 집합(`발표자료최종보고서장론`)에 15글자 모두 들어 있음 → F = 1.0 → P′ = 1.0. prior 0(OEM·legacy가 437이므로 949는 해당 없음) → 949 점수 **1.00**. GBK로도 유효(V = 1): 쌍 15개가 모두 0xB0~0xD7 / 0xA1~0xFE 안 → gb 15 → P = 1.0. 디코딩된 한자는 zh fixture(`资料报告`)에 하나도 없음 → F = 0 → P′ = 0.5 → 점수 **0.50**. 차 0.50 > 0.02 → 949가 1순위, 차 0.50 ≥ 0.1, 점수 1.00 ≥ 0.6 → `confident = true`.
- **`kr_ntfs-en-none`**: fixture 없음 → 949도 936도 F = 1 → P′ = 1.0 → 점수 1.00 / 1.00. 차 0 ≤ 0.02 → 동점. 순서표 [437, 949, 65001, 932, 936]에서 949 < 936 → 949 1순위. 차 0 < 0.1 → `confident = false`. 이것이 "표가 없는 동안 CP949와 GBK가 동점"이라는 F17 FR-17-8의 예상 동작이다.
- **`kr_ntfs-ko`(OEM 949, legacy 949)**: 949 prior 0.10 → 1.0 + 0.10 = **1.10**. 936은 0.50. 차 0.60 → 949 1순위, `confident = true`.
- **`kr_unix-ko`(OEM 949, legacy 65001, fixture)**: 949는 위와 같이 **1.10**, 936은 **0.50**. UTF-8은 이름 3개 모두 유효하지 않아 V = 0 → `score = prior`이고 legacy와 같으므로 **0.05**. 1순위 949, 차 0.60 → `confident = true`. (legacy가 949였던 이전 카드와 결과는 같지만 HostOS Unix의 기존 규칙을 반영한 입력이다.)
- **`utf8-*`**: UTF-8로 두 이름 모두 유효(V = 1), 선두 바이트(EB, EC, EA 등)가 이름마다 여러 개이므로 합 ≥ 2 → `utf8Forced = true` → 1순위 65001, 점수 1.00. 다른 후보는 두 이름 모두 CP949·SJIS·GBK로 유효하지 않아 V = 0 → DBCS는 `prior`만. 2순위는 437(0.05 + prior)이거나 OEM 코드페이지의 prior(0.10) 후보라서 차가 0.85 이상 → `confident = true`.
- **`jp-ko`(OEM 949, legacy 949, fixture)**: 감지 이름 2개, 글자 N = 8(`資料` 2 + `資料ひらがな` 6). Shift-JIS V = 1. kana 4(ひらがな), kanji1 4(`資`=8E91, `料`=97BF가 두 이름에 각각 한 번씩, 모두 0x889F~0x9872 안), half 0 → sw 8 → P = 1.0 → 932 점수 **1.00**(prior 없음). CP949는 같은 바이트를 UHC 한글로 읽어 ksx 0, hangul 8 → sw 0.3 x 8 = 2.4 → P = 0.3, F = 0(fixture 밖) → P′ = 0.15, prior 0.10 → **0.25**. 차 0.75 → 932 1순위, `confident = true`.
- **`cn-ko`/`cn-en`**: GBK로 쌍 6개가 모두 영역 안(`资`=D7CA에서 첫 바이트 D7은 상한 포함) → P = 1.0, F = 1(fixture 4글자가 모두 `资料报告`) → 936 점수 **1.00**. 다른 후보는 CP949가 0.43 이하(`cn-ko`), 그 밖은 더 낮아 차 ≥ 0.5 → `confident = true`.
- **`jp-en`(OEM 437)**: 932 1.00, 다른 후보 최고 0.15 이하 → `confident = true`.
- **`ascii`**: 0x80 이상 바이트가 있는 이름이 0개 → `totalCount = 0` → `kNoNonAsciiNames`.
- **`*-real` 4행**: T09의 실제 표 내용은 이 카드가 알 수 없으므로 손계산하지 않는다. 기대값은 F17 8절 문장(1a·2a는 CP949, `jp.zip`은 Shift-JIS, `cn.zip`은 GBK)이다. 932는 F가 없어 표와 무관하게 1.00이고(`jp-ko-real`), 949가 표를 가져도 UHC 읽기의 P′는 0.3 이하라 0.40 이하다. 936의 `cn-ko-real`은 P = 1.0, F ≥ 0이므로 0.50 이상이다. `kr_ntfs-en-real`·`kr_unix-ko-real`은 949와 936이 모두 P = 1.0이라 F의 차이가 승부를 가른다(한글 이름의 F가 GBK로 읽은 한자의 F보다 높아야 한다). 이 행들이 실패하면 표나 공식을 고치지 말고 13절 ST-4로 멈춘다.

위 풀이의 소수 둘째 자리까지의 값은 Python 참조 구현과 같음을 카드 작성자가 확인했다. CP949·GBK로 읽는 보조 후보(`jp-ko`의 949 0.25, `cn-*`의 949)의 점수는 디코더 구현 차이로 조금 다를 수 있으므로 정답 파일은 1순위·`utf8Forced`·`confident`만 비교한다.

### 14.3 예상 크기와 환경

- 예상 변경: 제품 코드 265줄(5.4절 `src/shared/encoding/` 합계), 테스트 515줄 → 합계 약 780줄(코퍼스·정답 파일 55줄은 테스트 데이터라 제외). [09 1절](../../docs/09-development-process.md)의 400줄 기준을 넘는다. 이유: 테스트를 먼저 쓰는 규칙에 따라 TC 17개와 통합 테스트 코드를 포함하고, 순위·동점·확신의 경계 처리가 대부분이기 때문이다. 원래 한 카드(약 1,300줄)에서 점수 공식과 빈도표를 G2-F17-T03·T09로 덜어 낸 크기다. 검수자가 이 이유를 승인해야 `준비됨`이 된다([README 6절](README.md)). 정지 조건 ST-9의 1.5배 상한은 이 합계 기준이다.
- 환경: Windows 11, Visual Studio 2026 또는 2022(MSVC, C++20), PowerShell 5.1 이상, 선행 작업이 만든 `tools/build.ps1`·`tests/unit/run.ps1`·`tests/integration/run.ps1`. 구현자는 네트워크를 쓰지 않는다.
- 시간: 외부 타임아웃은 M 크기라 30분이다([12 4.4](../../docs/12-agent-orchestration.md)). 예상 크기가 크므로 한 번의 실행으로 끝나지 않을 수 있다. 작업을 시작한 직후 `RESULT.md`를 `PARTIAL`로 만들고, 8절 ①(테스트 커밋) 직후와 ②(구현) 직후에 갱신한다. 테스트 작성(8절 표 → 코드)에 전체 시간의 절반 이상을 쓴다.

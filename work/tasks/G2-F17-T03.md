## 1. 배경

### 1.1 사용자 문제

ZIP은 파일 이름의 인코딩을 기록하지 않는 경우가 많다. 다른 로캘 Windows에서 CP949 ZIP을 열면 7-Zip은 `¹ßÇ¥ÀÚ·á`처럼 깨진 이름을 보여 주고, 그대로 풀면 깨진 이름의 파일이 생긴다([F17 1절](../../docs/05-feature-specs/F17-filename-encoding.md)). j-zip은 이름 바이트를 보고 가장 그럴듯한 인코딩을 자동으로 고른다. 이 "고르는 계산"은 세 카드로 나뉜다. 이 카드는 그중 **후보마다 점수를 매기는 공식**만 만든다. 후보를 줄 세우고 확신을 판정하는 일은 G2-F17-T08, 점수 공식에 주입할 상용 문자 빈도표 데이터는 G2-F17-T09가 한다.

### 1.3 구현에 필요한 사실 (인라인)

**후보와 단계.** 감지는 두 단계다. 1단계(G2-F17-T02): 0x80 이상 바이트를 가진 이름마다 후보 코드페이지로 엄격 디코딩해 보고 후보별 유효율 `V = 성공한 이름 수 / 0x80 이상 바이트를 가진 이름 수`를 구한다(FR-17-5). 2단계: `V`와 디코딩된 문자열로 점수를 매기고(이 카드, FR-17-7~9) 순위를 정한다(G2-F17-T08, FR-17-6·10~12). 후보는 UTF-8(65001), CP949(949), Shift-JIS(932), GBK(936), CP437(437)이고 시스템 `CP_OEMCP`/`CP_ACP`가 이 목록에 없으면 호출자가 후보에 더해 넘긴다(FR-17-4).

**7-Zip의 현재 규칙**(`upstream/7zip/CPP/7zip/Archive/Zip/ZipItem.cpp:405-462` `CItem::GetUnicodeString`): ① UTF-8 플래그 → ② Info-ZIP Unicode extra → ③ `-mcp` 지정값 → ④ Win32에서 HostOS가 Unix면 UTF-8 → ⑤ `GetCodePage()`(`ZipItem.h:338-350`: 중앙 디렉터리 HostOS가 FAT/NTFS/Unix면 `CP_OEMCP`, 아니면 `CP_ACP`, 중앙 디렉터리 정보가 없으면 `CP_OEMCP`). 점수기는 이 규칙이 이름 바이트에 실제로 쓸 코드페이지를 `legacyCodePage`로 입력받는다. 그 값은 **HostOS가 Unix이면 UTF-8(65001), 그 밖에는 `GetCodePage()` 결과**다(FR-17-9). 값을 계산해 넘기는 일은 호출자(G2-F17-T04)의 몫이고 이 카드는 받은 값으로 `prior`만 계산한다.

**UTF-8 유효성.** 기존 `Check_UTF8_Buf`(`upstream/7zip/CPP/Common/UTFConvert.cpp:230`, 선언 `UTFConvert.h:88`)가 있다. 이 카드는 UTF-8 유효성을 다시 구현하지 않는다. `V`는 입력으로 받는다.

**점수 공식**(FR-17-7~9, 숫자는 모두 제안값):

```
V         = validCount / totalCount
DBCS 후보(949, 932, 936), V >= 0.9:
    P     = (후보별 상용 문자 가중 합) / (디코딩된 비ASCII 문자 수 N)
    F     = 상용 문자 빈도표(한글 512자 / 간체 한자 512자)에 드는 문자 비율   [949, 936만]
    P'    = P x (0.5 + 0.5 x F)                                              [949, 936]
    P'    = P                                                                [932]
    score = V x P' + prior
DBCS 후보, V < 0.9:   score = prior                                          (P' = 0)
UTF-8:                score = V x 1.0 + prior            (P' = 1.0)
단일 바이트류(437 등, 목록의 그 밖 코드페이지 포함): score = 0.05 + prior
prior = 시스템 OEM 코드페이지와 같으면 0.10, 7-Zip 기존 규칙 코드페이지와 같으면 0.05, 둘 다면 0.10(합산 안 함)
```

**호출 위치.** 이 카드의 함수는 G2-F17-T08의 `ScoreCandidates`가 호출하고, `ScoreCandidates`는 G2-F17-T04가 `ZipHandler` 열기 훅에서 호출한다. 그 훅과 이름 결정 순서(FR-17-13)는 이 카드 밖이다.

### 1.4 작성 환경 한계

이 카드를 쓴 환경에는 C++ 컴파일러가 없어서 6절 선언을 컴파일해 보지 못했다. 8절의 기대값은 Python 참조 구현(카드 작성자가 7절 규칙을 그대로 옮긴 임시 스크립트)으로 계산한 값과 손계산이 일치함을 확인했다. 그 스크립트로 각 이름 바이트가 Windows 코드페이지(`cp949`, `cp932`, `cp936`, `cp437`, `cp950`)로 **엄격하게 디코딩되고 8절에 적은 문자가 나오는지**도 확인했다. 스크립트는 레포에 넣지 않는다.

## 6. 인터페이스 계약

모든 선언은 네임스페이스 `jzip::shared::encoding`이다. 파일 이름 규칙(snake_case)과 `#pragma once` 사용은 **제안(카드 결정)** 이다. 08에 파일 이름 규칙이 없다. 6.1~6.4절 선언은 컴파일해 보지 못했다(1.4절).

### 6.1 입력 타입 — 제안(G2-F17-T02 산출물, 이 카드는 읽기만 한다)

`src/shared/encoding/candidate_evidence.h`는 G2-F17-T02가 만든다. 이 카드는 아래 모양을 전제하며 T02 카드가 이 모양을 따라야 한다. **병합된 실제 헤더가 아래와 필드 이름·타입이 다르면 13절 ST-2로 멈춘다.** 이 카드는 그 파일을 수정하지 않는다.

```cpp
// src/shared/encoding/candidate_evidence.h  (G2-F17-T02 산출물)
using CodePage = std::uint32_t;                 // Windows 코드페이지 번호. 이미 있으면 그것을 쓴다

struct DecodedName {
  std::string_view bytes;                       // 원본 이름 바이트. 호출자가 소유하고 호출 동안 유효하다
  std::u16string   text;                        // 엄격 디코딩 결과(UTF-16). 후보 코드페이지가 UTF-8이거나 단일 바이트류이면 점수기는 text를 읽지 않는다
};

struct CandidateEvidence {
  CodePage                codePage;
  std::uint32_t           totalCount;           // 0x80 이상 바이트를 가진 이름 수 (모든 후보에서 같은 값)
  std::uint32_t           validCount;           // 엄격 디코딩에 성공한 이름 수
  std::vector<DecodedName> decoded;             // 성공한 이름만, 입력 순서 유지. decoded.size() == validCount
};
```

### 6.3 `ICommonCharSet` — 제안(카드 결정)

### 6.4 `ComputeCandidateScores` — 제안(시그니처는 카드 결정, 동작은 FR-17-7~9 확정)

`src/shared/encoding/candidate_score.h`.

```cpp
struct ScoringContext {
  CodePage systemOemCodePage;                      // jzip-win이 조회한 CP_OEMCP 실제 값(예: 437, 949). 0이면 어떤 후보와도 같지 않다
  CodePage legacyCodePage;                         // 7-Zip 기존 규칙이 이 이름들에 쓸 코드페이지(1.3절: Unix면 65001). 0이면 어떤 후보와도 같지 않다
  const ICommonCharSet* koreanCommon = nullptr;            // 한글 음절 상위 512자. nullptr이면 CP949의 F = 1.0
  const ICommonCharSet* simplifiedChineseCommon = nullptr; // 간체 한자 상위 512자. nullptr이면 GBK의 F = 1.0
};

struct ScoringInput {
  std::span<const CandidateEvidence> candidates;   // 호출자가 정한 순서(Encoding.Candidates 순서 + 시스템 코드페이지). 결과가 이 순서를 그대로 따른다
  ScoringContext context;
};

enum class DetectionStatus : std::uint8_t {
  kOk = 0,
  kNoNonAsciiNames,   // totalCount == 0 (FR-17-2)
  kInvalidInput,      // 7.1절 검사 실패
  kInternalError      // 내부 할당 실패 등 예외를 잡았을 때
};

struct CandidateScore {
  CodePage codePage = 0;
  double   validityRate = 0.0;    // V
  double   plausibility = 0.0;    // P'. UTF-8은 1.0, V < 0.9인 DBCS와 단일 바이트류는 0.0
  double   prior = 0.0;
  double   score = 0.0;           // 상한 없음(최대 1.10)
};

struct CandidateScoreSet {
  DetectionStatus status = DetectionStatus::kOk;
  std::vector<CandidateScore> scores;   // 입력 candidates와 같은 순서·같은 개수. status != kOk이면 비어 있다
};

CandidateScoreSet ComputeCandidateScores(const ScoringInput& input) noexcept;
```

- Input: 위 `ScoringInput`. 사전조건은 7.1절. 이름 바이트(`string_view`)는 호출 동안만 읽고 보관하지 않는다.
- Output: `CandidateScoreSet`. `status == kOk`이면 `scores.size() == candidates.size()`.
- 오류: 예외를 던지지 않는다(`noexcept` + 함수 전체를 `try { … } catch (...) { return {kInternalError, …}; }`로 감싼다). 입력 오류는 `kInvalidInput`, 이름 없음은 `kNoNonAsciiNames`.
- 부작용: 없음. 파일·레지스트리·네트워크·OS 호출 없음, 전역 가변 상태 없음, 시계·난수 없음. Release에서는 로그도 없다(11절).
- 스레드: 재진입 가능, 입력이 `const`이므로 같은 입력으로 여러 스레드가 동시에 호출해도 된다.
- 성능: 이름 길이에 비례하는 힙 할당과 문자 단위 힙 할당을 하지 않는다(결과 벡터 외 작은 보조 배열만 허용). 이름 2,000개 × 후보 5개를 Release x64에서 20ms 이하(TC-19, 출처: 카드. F17 5절 50ms 중 이 단계 몫으로 카드가 정함).
- 내부 구조(`plausibility.h`의 `detail` 함수 이름 등)는 구현자가 정한다. 위 공개 타입과 동작만 계약이다. G2-F17-T08이 이 공개 타입을 그대로 쓰므로 핸드오프 뒤 바꾸려면 카드 개정이다.

## 7. 동작 명세

### 7.1 입력 검사 (R-1) — 제안(카드 결정)

순서대로 검사하고 첫 실패에서 끝낸다. `status`와 빈 `scores`로 돌려준다.

| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | `candidates`가 비어 있음 | `kInvalidInput` |
| 2 | 같은 `codePage`가 두 번 있음 | `kInvalidInput` |
| 3 | 어떤 후보든 `validCount > totalCount` 또는 `decoded.size() != validCount` | `kInvalidInput` |
| 4 | 후보들의 `totalCount`가 서로 다름 | `kInvalidInput` |
| 5 | `totalCount == 0` | `kNoNonAsciiNames` (FR-17-2) |

### 7.2 후보 종류와 점수 (R-2) — 확정(FR-17-9) + 확정(F17 2026-10-14 보충)

후보를 코드페이지로 세 종류로 나눈다: UTF-8(65001), DBCS(949, 932, 936), 단일 바이트류(그 밖 전부, 437 포함. 시스템 코드페이지가 950처럼 다른 DBCS여도 점수 공식이 정의돼 있지 않으므로 단일 바이트류로 취급한다 — FR-17-9).

| 종류 | 조건 | `plausibility` | `score` | 출처 |
|---|---|---|---|---|
| UTF-8 | 항상 | 1.0 | `V x 1.0 + prior` | FR-17-9(UTF-8 P′ = 1.0 보충. F17 7절 그림 "UTF-8 12%"가 `V`만 반영하는 것과 맞음) |
| DBCS | `validCount x 100 >= totalCount x 90` (V ≥ 0.9) | 7.3절 P′ | `V x P′ + prior` | FR-17-7~9 |
| DBCS | 위 조건 불만족 | 0.0 | `prior` | FR-17-7("V < 0.9인 DBCS는 prior만" 보충) |
| 단일 바이트류 | 항상 | 0.0 | `0.05 + prior` (V를 쓰지 않음) | FR-17-9 |

`V = validCount / totalCount`(double). `prior`: `codePage == systemOemCodePage`이면 0.10, 아니면 `codePage == legacyCodePage`이면 0.05, 아니면 0.0. 둘 다 같으면 0.10(합산하지 않는다, FR-17-9). `ScoringContext`의 두 값이 0이면 어떤 후보도 0이 아니므로 해당 prior는 없다.

### 7.3 DBCS의 P, F, P′ (R-3) — 확정(FR-17-7·8, 숫자 출처 표 7.4) + 제안(영역 걷기 방식)

대상은 `validCount > 0`인 `decoded` 전부다(성공한 이름만). 먼저 **글자 수 N** = 모든 `text`에서 코드 단위가 0x80 이상인 것의 개수. `N == 0`이면 P′ = 0.0(0으로 나누지 않는다).

**바이트 걷기(walker).** 이름 바이트를 왼쪽에서 오른쪽으로 읽는다. 바이트 `b`가 0x80 미만이면 1바이트 ASCII로 넘어간다. 그 밖에는 코드페이지별로:

| 코드페이지 | 규칙 |
|---|---|
| 949, 936 | `b`가 0x81~0xFE이고 다음 바이트가 있으면 (b, 다음) 2바이트 쌍으로 읽고 2칸 전진. 아니면 1바이트 단일로 읽고 1칸 전진 |
| 932 | `b`가 0xA1~0xDF이면 반각 가타카나 단일(1칸). `b`가 0x81~0x9F 또는 0xE0~0xFC이고 다음 바이트가 있으면 2바이트 쌍(2칸). 아니면 1바이트 단일(1칸) |

이름마다 따로 걷는다(이름 경계를 넘지 않는다). 아래 개수는 모든 이름의 합이다.

**CP949 (949).** 가중 합 `sw = ksx x 1.0 + uhc x 0.3`.
- `hangul` = `text`에서 U+AC00~U+D7A3인 코드 단위 수.
- `ksx` = 쌍 중 첫 바이트 0xB0~0xC8 **그리고** 둘째 바이트 0xA1~0xFE인 쌍 수(KS X 1001 완성형 2,350자 영역, FR-17-7).
- `uhc` = `max(0, hangul - ksx)`(확장 완성형. 0.3만 인정).
- 한글 음절이 아닌 비ASCII 문자(한자, 기호, 호환 자모 등)는 가중치 0.

**Shift-JIS (932).** `sw = kana x 1.0 + half x 0.2 + kanji1 x 1.0`.
- `kana` = `text`에서 U+3040~U+30FF인 코드 단위 수(히라가나·가타카나).
- `half` = 걷기에서 읽은 반각 가타카나 단일 바이트(0xA1~0xDF) 수.
- `kanji1` = 쌍 중 `(첫 바이트 x 256 + 둘째 바이트)`가 0x889F 이상 0x9872 이하인 쌍 수(JIS X 0208 제1수준 한자의 Shift-JIS 영역. 제2수준은 0x989F부터. FR-17-7 보충으로 명세에 반영).
- 그 밖의 문자(제2수준 한자, 기호 등)는 가중치 0.

**GBK (936).** `sw = gb`. `gb` = 쌍 중 첫 바이트 0xB0~0xD7 **그리고** 둘째 바이트 0xA1~0xFE인 쌍 수(GB2312 1급 한자 영역, FR-17-7). 그 밖은 0.

**P** = `min(1.0, sw / N)`.

**F와 P′.**
- 949: `koreanCommon != nullptr`이면 `F = (text에서 0x80 이상 코드 단위 중 koreanCommon->Contains(u)가 true인 수) / N`, nullptr이면 `F = 1.0`. `P′ = P x (0.5 + 0.5 x F)`.
- 936: 같은 방식, 집합은 `simplifiedChineseCommon`. `P′ = P x (0.5 + 0.5 x F)`.
- 932: F 없음(FR-17-8의 빈도표는 한글·간체뿐). `P′ = P`(FR-17-8 보충).

### 7.4 숫자 출처

| 값 | 출처 |
|---|---|
| 0.9(V 임계), 0.3, 0.2, 0.10, 0.05, 0.5+0.5F | 문서: FR-17-7~9 (F17 9절이 제안값이라고 밝힘) |
| 0.05 + prior(단일 바이트류) | 문서: FR-17-9 |
| 영역: 0xB0~0xC8 / 0xA1~0xFE, 0xB0~0xD7 / 0xA1~0xFE, U+3040~U+30FF, 0xA1~0xDF, U+AC00~U+D7A3 | 문서: FR-17-7 |
| 영역: 0x889F~0x9872 | 문서: FR-17-7 보충(JIS X 0208 제1수준 한자의 Shift-JIS 코드 범위. 제2수준은 0x989F부터) |
| UTF-8 P′ = 1.0, V<0.9 DBCS의 점수 = prior, 그 밖 코드페이지를 단일 바이트류로 취급 | 문서: FR-17-9 보충 |
| 20ms(TC-19) | 카드(F17 5절 50ms의 일부) |

### 7.5 경계 사례

| 상황 | 동작 |
|---|---|
| 어떤 후보의 `validCount == 0` | `V = 0`. DBCS는 임계 미달이라 `score = prior`, UTF-8은 `score = prior`, 단일 바이트류는 `0.05 + prior` |
| `systemOemCodePage == legacyCodePage` | prior는 0.10(합산하지 않음) |
| `systemOemCodePage`나 `legacyCodePage`가 0 | 어떤 후보도 0이 아니므로 해당 prior는 없다 |
| `legacyCodePage == 65001`(Unix HostOS) | UTF-8 후보에 prior 0.05(시스템 OEM과 같으면 0.10) |
| `text`에 U+0080 이상이 없는데 DBCS 임계를 넘음 | N = 0 → P′ = 0.0 |
| `text`가 서로게이트 쌍을 가짐 | 코드 단위마다 센다(949·932·936은 BMP만 만들므로 정상 입력에서는 없다) |
| 점수가 1.0을 넘음(최대 1.10) | 그대로 돌려준다. 퍼센트 상한(100)은 G2-F17-T08이 적용한다 |
| 후보 하나만 있음 | 그 후보의 점수만 계산한다 |

### 7.6 오류 처리

예외를 던지지 않는다. 입력 오류는 `kInvalidInput`, 내부 예외는 `kInternalError`. `scores`는 비어 있다. 호출자(G2-F17-T08을 거쳐 G2-F17-T04)는 `kOk`가 아니면 감지 결과를 쓰지 않고 7-Zip 기존 규칙으로 돌아간다(그 분기는 이 카드 밖).

## 8. 테스트 계획

**먼저 쓴다.** 순서: ① `tests/unit/encoding/**`를 만들어 **컴파일되지만 실패하는** 상태로 커밋한다(6절 선언만 있는 빈 구현이 `kInternalError`를 돌려주게 해서 컴파일은 되게 한다) → ② 구현 → ③ 통과. ①의 커밋 SHA를 RESULT 보고서에 적는다. 이후 테스트 파일의 기대값은 바꾸지 않는다(DC-9).

도우미(`evidence_builder.h`)가 만드는 것:
- `MakeEvidence(codePage, totalCount, {{"<16진 바이트>", u"<텍스트>"}, …})` → `CandidateEvidence`. `validCount`는 이름 수와 같다. 같은 이름 바이트를 여러 번 이어 붙이는 `Repeat("B0A1", 49)` 같은 보조 함수를 둘 수 있다.
- 모든 텍스트는 `u"가"`처럼 **`\u` 이스케이프**로 쓴다(소스 파일 인코딩에 의존하지 않는다).
- `FixedCharSet({u'가', …})` → `ICommonCharSet` 테스트 구현.
- 아래 표의 문자는 한글로 적었지만 소스에는 이스케이프로 쓴다. 문자 ↔ 바이트(코드페이지): `가`=U+AC00(B0A1, 949), `똠`=U+B620(8C63, 949, KS X 밖), `ㅋ`=U+314B(A4BB, 949, 한글 음절 아님), `힝`=U+D79D(C8FE, 949), `컿`=U+CEFF(B0A0, 949, UHC), `갂`=U+AC02(8141, 949, UHC), `伽`=U+4F3D(CAA1, 949, 한자), `아`=U+C544(EC9584, UTF-8), `あ`=U+3042(82A0, 932), `ｱ`=U+FF71(B1, 932), `資`=U+8CC7(8E91, 932), `、`=U+3001(8141, 932), `亜`=U+4E9C(889F, 932), `腕`=U+8155(9872, 932), `弌`=U+5F0C(989F, 932), `ⅰ`=U+2170(FA40, 932), `资`=U+8D44(D7CA, 936), `丂`=U+4E02(8140, 936), `啊`=U+554A(B0A1, 936), `剥`=U+5265(B0FE, 936), `亍`=U+4E8D(D8A1, 936), `盃`=U+76C3(B0A0, 936), `Θ`=U+0398(E9, 437), `一`=U+4E00(A440, 950).
- 단일 바이트류 후보(437, 950)는 점수기가 `text`를 읽지 않지만 도우미는 위 문자를 채운다.
